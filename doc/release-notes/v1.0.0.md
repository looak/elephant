## v1.0.0 "Herd"

The first complete, multi threaded Elephant. Elephants move as a herd, so do the search threads now: they share one
transposition table and spread out over different depths instead of all doing the same work. 1.0 also means every
advertised UCI option works and every valid UCI command gets an answer.

On four threads 1.0 is about +200 Elo over 0.15.2 on one. On a single thread it plays like 0.15.2, this cycle was
about correctness and robustness, the next one is about strength again.

### Transposition table
- Buckets of 8 entries, one 64 byte cache line, a probe reads a single line. Each entry is one 64-bit word written and
  read atomically, threads sharing the table never see half an entry.
- Twice the entries per megabyte, and a new result always finds a slot, the least valuable entry in the bucket makes
  room. The old table dropped shallower results, exact scores too, once a slot held a deeper entry from the same search.
- A fail-low no longer wipes the stored move.
- Every megabyte of `Hash` is used, `Hash 100` was 64 MB before. The maximum goes from 1 GB to 32 GB, and the table is
  cleared with all threads.
- `info hashfull`.

### Lazy SMP
- Thread 0 is the main thread, it reports, manages time and its move is played. It stops the helpers when it's done.
- Helpers skip iterations in staggered blocks, they search ahead of the main thread and fill the table with deeper
  results.
- `info nodes` and `go nodes` count every thread.
- `debug on` prints what the helper threads search as info strings.

### UCI
- `ucinewgame` clears the transposition table, games no longer influence each other.
- `go nodes`, `go mate` and `go searchmoves` work, they used to stop the engine without a bestmove.
- A malformed command reports an `info string error` and the engine keeps running.
- `Threads` 1–64, `Hash` 1–32768.

### Fixes
- Threefold repetitions after a double pawn push were missed: the en passant square was set and hashed even when no
  pawn could capture, so the same position reached two ways hashed differently. fastchess reported "PV continues after
  threefold repetition".
- A FEN with black to move was hashed without the side to move key, the same position reached by moves hashed
  differently (#13).
- A non-pawn move onto the en passant square was flagged as an en passant capture (#14).
- The fifty move counter wasn't reset by a pawn push (#15).
- The bench measured mostly the OS mapping in a new 64 MB table for every position, it now measures the search.

### Under the hood
- The legacy move generator is gone, the staged tusk generator the search has used since 0.14 is the only one. The
  move generator tests stay parameterized on the generator, ready to A/B a new one.
- Builds with assertions check at every node that the incremental hash equals a full recompute.
- Two test tiers: a smoke tier, unit tests, perft, bench and node-limited EPD suites (WAC, STS) in about a minute
  before every merge, and an extended tier (WAC, STS, Arasan 2024 with 1 and 4 threads) in CI. Every suite has a
  baseline that warns and a minimum that fails. EPD files with comments containing `=`, coordinate notation in STS
  score lists and lines missing a comma are read correctly.

### Speed
Perft 6 from the start position about 140M moves/s, search from the start position about 4.5M nps, bench 503240
nodes at 4.4M nps. One thread, the g++ build OpenBench uses (`-O3 -march=native`), AMD Ryzen 9 9900X.
